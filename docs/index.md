# AceMQ for .NET

AMQP for C# and VB.NET: the same message envelope, the same patterns and the same
metric names as the [JVM libraries](https://acemq.org/), with an API that reads like
.NET rather than transliterated Java.

> **Pre-1.0.** Publishing, consuming, topology, request/reply, ordering, pipelines,
> the outbox, replay and streams all work against a real broker, with an integration
> suite that runs against RabbitMQ in CI. The API is still free to change.

## What it looks like

```csharp
using var mq = await AceMqConnection.ConnectAsync("amqp://localhost");

using var consumer = await mq.ConsumeAsync<OrderPlaced>("orders.placed", async message =>
{
    await _orders.RecordAsync(message.Payload);
    return Ack.Accept();
});

var publisher = mq.Publisher<OrderPlaced>("orders", "order.placed");
await publisher.SendAsync(new OrderPlaced("A-1", 42.50m));
```

## Two languages, one assembly

C# and VB.NET compile to the same IL, so both reference the same package. There is
no separate VB library and there will not be one.

```vb
' VB.NET -- the same assembly, the same types
Dim publisher = mq.Publisher(Of OrderPlaced)("orders", "order.placed")
Dim result = Await publisher.SendAsync(New OrderPlaced("A-1", 42.5D))
```

What that costs is discipline on the public API rather than a second
implementation: nothing on the surface that VB cannot call, which rules out
`Span<T>` and `ref struct` in signatures, members that differ only by case, and
overloads separable only by optional arguments. The VB example is compiled **and
run** in CI for that reason — it has already caught two differences that would
otherwise have reached a release. See [VB.NET](vbnet.md).

## What the library does

| | |
|---|---|
| Publishing | confirms by default, back pressure, unroutable messages reported rather than dropped |
| Consuming | explicit dispositions — accept, retry, dead-letter, release — and an attempt counter |
| Topology | exchanges, queues and bindings declared as one unit, dead-letter wiring included, with a dry run |
| Codecs | JSON, XML, text and bytes; composite for a format migration; payload encryption |
| Request/reply | one reply queue per requester, replies matched by correlation |
| Ordering | order per key across partitions, and a partition that halts rather than reorders |
| Pipelines | steps on their own queues, type-checked against each other |
| Outbox | write the message with your data, publish it after the commit |
| Replay | put dead-lettered messages back, all of them or the ones that match |
| Streams | read from an offset; consuming removes nothing |
| Security | TLS with verification on by default, private CAs, client certificates, credential providers |
| Reliability | retry policies with jitter, idempotency, drain before shutdown |
| Metrics and tracing | the same metric names as Java; a trace crosses the broker and the language |
| Transports | RabbitMQ, and an in-process broker for tests |
| The envelope | identity, correlation, causation, attempt, origin — pinned by conformance tests |

## Why the envelope came first

A port is only "the same library" if something proves it. The proof here is a set of
fixtures **generated by publishing through the Java library** and reading the message
back at the transport level — not copied from documentation.

Two implementations agreeing with the same prose is not interoperability. Agreeing
with the same bytes is.

That exercise immediately pinned six behaviours no document stated plainly, any of
which would have been a coin flip if transcribed by hand. They are on [the
envelope](envelope.md) page.

## Where it runs

`netstandard2.0`, which reaches **.NET Framework 4.6.2+**, .NET Core and modern .NET
from one assembly — and the RabbitMQ transport reaches the same, because
`RabbitMQ.Client` still ships a `netstandard2.0` build.

That is deliberate rather than conservative. The applications most likely to want a
supported AMQP library are the ones that cannot easily move, and `netstandard2.0` is
the only target that reaches all of them at once.

## The rest of AceMQ

The JVM libraries — the AMQP core, its Spring Boot starter, the RabbitMQ management
API and the load generator — are at **[acemq.org](https://acemq.org/)**.

The wire contract, the metric names and the conformance suite are shared and
single-sourced there. This site is where the .NET libraries are documented, not
where the specification lives.
